Alguns valores ainda vêm do arquivo .env do servidor. Ao salvar aqui, passam a valer os desta tela.

1

Conta que envia os e-mails

Cada e-mail sai da conta de quem está logado na Gestão TI: o e-mail cadastrado no AD, com o mesmo login e senha da rede. Não há conta nem senha para cadastrar aqui. Vale para os disparos, para a senha do Wi-Fi Visitante e para os testes desta tela.

Os e-mails saem deste endereço, e ele também é o usuário de login no servidor.

2

Servidor de e-mail

Escolha o tipo: servidor, porta e segurança são preenchidos sozinhos.

3

Disparos de e-mail dos usuários

Os envios usam o servidor do item 2 com o login e a senha do AD de quem está logado. A senha é a do próprio login na Gestão TI (fica criptografada na sessão e some ao sair); só é pedida de novo se o servidor de e-mail recusar. Num disparo, ela fica guardada com criptografia só até ele terminar.

Como o servidor de e-mail espera o usuário. Na dúvida, teste com “Enviar teste para mim” na tela de disparos.

1 crédito = 1 disparo. Com 0, a pessoa precisa pedir créditos (ou receber no módulo Créditos de e-mail) antes do primeiro disparo.

Todo e-mail enviado pela Gestão TI leva este endereço em “Responder para”: quem clicar em Responder escreve para ele, e não para quem enviou. O campo “Responder para” dos disparos fica travado com este valor. Deixe vazio para cada disparo escolher.

Aparece em letra pequena, separado por uma linha, no fim de todo e-mail. Deixe vazio para não colocar aviso.

4

Limites dos disparos

Vazio = sem limite. Microsoft 365 e Google: até 30.

5

Wi-Fi Visitante (banco do portal)

O portal do Wi-Fi de visitantes guarda os cadastros e as senhas num banco MySQL. A Gestão TI lê esse banco para listar os visitantes e grava lá a senha nova quando a TI troca. O visitante entra com a senha nova na hora.

Banco de dados (MySQL)

IP ou nome do servidor onde está o MySQL do portal.

Quase sempre 3306.

O banco (schema) do portal. No servidor atual: radio.

Usuário do MySQL (não é o usuário do servidor). Recomendado: um usuário só para a Gestão TI, veja abaixo.

Acesso ao servidor

Deixe vazio se for o mesmo servidor do banco.

Quase sempre 22.

Usuário de login no Linux do servidor (o mesmo usado no SSH/PuTTY).

Tabelas do portal (avançado)

Nome, CPF, e-mail, celular e se o cadastro está ativo. A coluna idradcheck liga o cadastro ao login.

Login (username) e senha (value) do RADIUS. A senha fica em código (ex.: MD5), conforme a coluna attribute; a Gestão TI grava no mesmo formato.

Recomendado: criar um usuário do MySQL só para a Gestão TI

Em vez do root, entre no servidor do banco (SSH/PuTTY), abra o MySQL com mysql -u root -p (ou sudo mysql) e rode os comandos abaixo, trocando a senha. Depois use gestaoti e essa senha nos campos acima, com “Conectar por SSH” marcado.

CREATE USER 'gestaoti'@'localhost' IDENTIFIED BY 'uma-senha-forte';
CREATE USER 'gestaoti'@'127.0.0.1' IDENTIFIED BY 'uma-senha-forte';
GRANT SELECT, UPDATE ON radio.reg_users TO 'gestaoti'@'localhost', 'gestaoti'@'127.0.0.1';
GRANT SELECT, UPDATE ON radio.radcheck  TO 'gestaoti'@'localhost', 'gestaoti'@'127.0.0.1';
FLUSH PRIVILEGES;

Com isso a Gestão TI só consegue ler e alterar essas duas tabelas. Por que não o root: em muitos servidores o root do MySQL só entra pelo terminal do próprio servidor e recusa programas.
